The arithmetic, stated plainly. Ten components in CoALA's framework. Five we keep faithfully — working memory, episodic memory, procedural memory, retrieval, reasoning — and a sixth, episodic learning, which I under-counted until I read §4.5 again. Two we keep in reduced form — semantic memory is read-only, grounding is far more specified than the paper requires. Four learning actions we do not have, of which one is a considered refusal and three are staging. One component is ours alone — the decision procedure, which the paper leaves open and we close by making the model the sole decider.

3 · The four components that match exactly

These are worth reading closely, because "we follow CoALA" is a claim that is usually made loosely and is rarely true in the details.

Working memory kept

The paper is unusually specific: "a data structure that persists across LLM calls", whose subset is synthesised into each prompt and into which output is parsed back, and which it calls "the central hub connecting different components."

Ours does exactly this. compose() returns five parts; absorb() parses the model's JSON back into variables.

memory.py:400, :423, :437

Episodic memory kept

Paper: experience from earlier decision cycles, retrieved during planning, and — note — writable as a form of learning. Ours stores one episode per beat and retrieves six.

The decay and the budget are ours, not theirs. So is the fact that we never consolidate.

memory.py:196, :286, :437

Procedural memory kept

Paper: implicit weights plus explicit code, "must be initialized by the designer", and writing is "significantly riskier … can subvert its designers' intentions."

Ours holds only the action vocabulary, and no write path exists. We took the warning as a design constraint rather than a caution to note.

Reasoning actions kept

Paper: reasoning "reads from and writes to working memory", and is the only action that does both — retrieval only reads, learning only writes to long-term.

Our decide() is that action and nothing else. This is the cleanest single correspondence in the system.

4 · The three differences that actually matter

Everything below is a place where we are not simply "implementing CoALA", and in each case the difference has a consequence for your experiment rather than being a stylistic choice.

Retrieval is automatic here divergence

In CoALA, retrieval is an action in the space — something the agent may choose to do, subject to the same decision procedure as everything else. That is why they call it an action at all.

In ours, retrieval happens before the decision, inside compose(). The model never elects whether to remember. So the agent cannot decide to look something up, and cannot decide not to.

Consequence: we cannot study the retrieval decision, only retrieval's effect.

memory.py:423 · retrieval is a fixed step, not a chosen action

The decision procedure is closed, not specified ours

The paper is explicit that it declines to specify this, and that most real agents collapse proposal, evaluation and selection into a single LLM call.

We collapse it into one call and delete the alternative. Line 893 returns before the rules argmax can run. So there is exactly one decider, ever.

Consequence: the decision procedure is not a variable we can ablate. We cannot compare "LLM decides" against "rules decide" inside one run.

cognition.py:821, :893

Learning stops at ① absent

Of the paper's five learning actions we perform exactly one — storing experience. The paper is explicit that ② semantic is the safe one, and gives Reflexion as the working example.

So our agent can remember that beat 34 was bad. It cannot conclude "therefore stop doing X." That is the honest boundary.
